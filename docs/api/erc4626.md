# `VestingEscrow4626` API

`VestingEscrow4626` vests principal denominated in a vault's underlying asset
while holding and transferring ERC-4626 shares. This page describes its
complete external surface, roles, units, schedule, authorization, and events
for the deployed 0.4.0 contracts.

The Ethereum mainnet implementation is
[`0x569C2E7045dCbEf8B77b092D25dBBAf3A37E665A`](https://etherscan.io/address/0x569c2e7045dcbef8b77b092d25dbbaf3a37e665a#code).
Applications should create minimal proxies through the
[0.4.0 factory](factory.md).

The detailed principal/yield split, gain/loss behavior, and rounding derivation
are in the [ERC-4626 accounting guide](../erc4626.md).

## Roles

| Role | Authority |
| --- | --- |
| `recipient` | Owns vested principal, may route its own principal claims to any valid receiver, and controls permissionless principal claiming. |
| `revoker` | May stop vesting immediately and route unvested principal shares to any valid receiver, or permanently renounce that authority. |
| `yield_recipient` | Fixed destination for all yield shares. It has no authority merely by being the destination. |
| third-party caller | May trigger a permissionless principal claim only to `recipient` and may trigger a yield claim only to `yield_recipient`. |
| `receiver` | Receives one principal or revocation transfer and gains no persistent authority. It cannot be zero or the escrow itself. |

A zero `revoker` makes the escrow irrevocable from initialization. A nonzero
revoker cannot be the escrow proxy itself.
`yield_recipient` is always nonzero and cannot be changed.

## Units

| Name | Unit |
| --- | --- |
| `principal_assets` | Underlying assets |
| `claimed_principal_assets` | Underlying assets |
| `claimable_principal_assets()` | Underlying assets |
| `max_principal_assets` | Underlying assets |
| `preview_principal_claim()` first return value | Underlying assets |
| `preview_principal_claim()` second return value | Vault shares |
| `claimable_yield_shares()` | Vault shares |
| `claim_principal()` return value | Vault shares |
| `claim_yield()` return value | Vault shares |

Do not interpret the return value of `claim_principal()` as an asset amount.
The `PrincipalClaim` event records both units.

## Initialization

```vyper
__init__()

initialize(
    revoker: address,
    vault: address,
    recipient: address,
    principal_assets: uint256,
    start_time: uint256,
    end_time: uint256,
    cliff_length: uint256,
    permissionless_claims: bool,
    yield_recipient: address,
) -> bool
```

Applications should deploy through the
[`VestingEscrowFactory`](factory.md), which quotes shares, applies the caller's
share limit, funds the proxy, and initializes it atomically. Each proxy can
initialize only once, and the implementation contract disables its own
initializer in its no-argument constructor.

Initialization stores the caller's exact asset-denominated
`principal_assets`; it does not derive principal from the funded balance. It
requires:

- `0 < principal_assets <= 2**128 - 1`;
- a recipient distinct from zero, the proxy, vault, and revoker;
- a revoker distinct from the proxy, or zero for an irrevocable escrow;
- `end_time` later than both the current block and `start_time`;
- a duration no greater than `2**64 - 1`;
- `cliff_length` no greater than the duration;
- a nonzero vault-share balance whose current asset value covers principal;
- a valid underlying asset contract;
- a nonzero `convertToShares(principal_assets)` result no greater than the
  funded share balance;
- a `yield_recipient` distinct from zero, the proxy, vault, and underlying
  asset.

## Schedule and lifecycle state

Let `S = start_time`, `E = end_time`, `C = cliff_length`, and
`P = principal_assets`. Principal vested at time `t` is:

```text
0                                      when t < S + C
P                                      when t >= E
floor(P * (t - S) / (E - S))           otherwise
```

The schedule is always measured in underlying assets. The cliff gates the
running linear schedule; at `S + C`, the accumulated amount becomes claimable
at once.

`disabled_at()` is zero until revocation. While it is zero, the effective
vesting stop is `end_time`. Revocation stores the current block timestamp,
freezes vesting there, and clears `revoker`. Renouncing revocation clears
`revoker` but leaves `disabled_at()` at zero and does not stop vesting.

## Configuration and accounting views

```vyper
recipient() -> address
vault() -> address
start_time() -> uint256
end_time() -> uint256
cliff_length() -> uint256
principal_assets() -> uint256
claimed_principal_assets() -> uint256
disabled_at() -> uint256
revoker() -> address
yield_recipient() -> address
permissionless_claims() -> bool

claimable_principal_assets() -> uint256
preview_principal_claim(max_principal_assets: uint256)
    -> (principal_assets: uint256, shares: uint256)
claimable_yield_shares() -> uint256
```

`principal_assets()` is the exact deployment-time promise and does not rebase
with vault performance. `claimed_principal_assets()` tracks schedule
entitlement consumed, while the contract transfers shares.

`preview_principal_claim()` returns the asset entitlement consumed and the
shares transferred under the vault's current conversion rate. Vault state can
change between preview and execution.

If a very small partial claim previews positive assets but zero shares,
execution reverts without consuming principal entitlement. Wait for more
principal to vest or request a larger amount.

## Principal claim

```vyper
claim_principal(
    receiver: address,
    max_principal_assets: uint256,
) -> uint256
```

Claims the smaller of currently vested, unclaimed principal and
`max_principal_assets`. It advances `claimed_principal_assets` by that asset
amount, transfers the corresponding principal shares, and returns the shares
transferred. Passing `2**256 - 1` claims all currently available principal.

Authorization is:

| Caller | Receiver | Permissionless claims enabled | Result |
| --- | --- | --- | --- |
| `recipient` | Any address except zero or the escrow | Either | Allowed |
| Anyone else | `recipient` | Yes | Allowed |
| Anyone else | Any other address | Either | Rejected |
| Anyone else | `recipient` | No | Rejected |

Permissionless claiming grants execution, not routing.

When no assets are claimable or `max_principal_assets` is zero, the function
returns zero without changing accounting or emitting `PrincipalClaim`.
Positive asset claims that would transfer zero shares revert.

## Yield claim

```vyper
claim_yield() -> uint256
```

Anyone may call after initialization. The function transfers all currently
claimable yield shares to the fixed `yield_recipient`, returns the shares
transferred, and emits `YieldClaim` when the amount is nonzero. The caller
cannot redirect yield.

## Revoke

```vyper
revoke(receiver: address)
```

Only the current `revoker` may call. The function:

1. Requires a receiver other than zero or the escrow and a current timestamp
   before `end_time`.
2. Computes the vested and unvested principal at the current timestamp.
3. Splits the current balance into principal and yield shares.
4. Computes the unvested principal share allocation.
5. Stores the current timestamp in `disabled_at` and clears `revoker` before
   external transfers.
6. Transfers unvested principal shares to `receiver`.
7. Leaves current yield and vested, unclaimed principal shares in the escrow.
8. Emits `Revoked`.

Revocation is immediate, final, and cannot be scheduled for a future timestamp.
Under vault loss, vested and unvested outstanding principal share the loss
proportionally. Current yield remains available through the separate,
permissionless `claim_yield()` operation.

## Renounce revocation

```vyper
renounce_revocation()
```

Only the current `revoker` may call. It permanently clears `revoker` without
stopping vesting and emits `RevocationRenounced`. Subsequent revocation and
renunciation calls are unauthorized.

## Permissionless principal claiming

```vyper
set_permissionless_claims(enabled: bool)
```

Only `recipient` may call. It changes whether third parties may execute
principal claims to the recipient; it never permits a third party to choose
another receiver. The function emits `PermissionlessClaimsSet`.

This setting does not affect `claim_yield()`, which is always permissionless
because its destination is fixed.

## Events

```vyper
event PrincipalClaim:
    receiver: indexed(address)
    principal_assets: uint256
    shares: uint256

event YieldClaim:
    recipient: indexed(address)
    shares: uint256

event Revoked:
    recipient: indexed(address)
    revoker: indexed(address)
    receiver: indexed(address)
    unvested_principal_assets: uint256
    shares: uint256
    ts: uint256

event RevocationRenounced:
    revoker: indexed(address)

event PermissionlessClaimsSet:
    enabled: bool
```

`PrincipalClaim.principal_assets` and `Revoked.unvested_principal_assets` are
underlying asset units. Every `shares` field is a raw vault-share amount.
`Revoked.shares` is the actual share transfer to the revocation receiver; under
vault loss, its current asset value can be less than
`unvested_principal_assets`.

## Vault behavior

The vault share token must remain transferable and move the exact requested
balance. Its `asset()`, `convertToAssets()`, and `convertToShares()` behavior
must remain compatible with the assumptions in the
[accounting guide](../erc4626.md).

Pauses, blacklists, transfer fees, rebasing share balances, incompatible
upgrades, and economically coarse share precision are unsupported. Direct
share donations participate in the principal/yield split; unrelated tokens
have no recovery method.
